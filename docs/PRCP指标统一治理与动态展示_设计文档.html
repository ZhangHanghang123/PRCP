需求与现状诊断

1.1 需求原文拆解

① 展示动态化：首页 KPI 区从固定 8 个 → 支持动态多选； 右上角齿轮按钮 → 列出方案对应全部指标 → 多选 → 选中才展示。
② 指标定义统一：资产余额、负债余额、贷款加权平均利率也纳入指标方案定义； 指标加"是否评分"标识 —— 不选则只计算不评分； 首页展示指标值时来源与定义统一。

1.2 现状：8 处硬编码

#位置硬编码内容后果
1后端 reverse_dashboard.pyDEFAULT_METRIC_TYPES = ["ROE","CET1","LCR","NSFR","DELTA_EVE"] 引擎算出更多指标也不展示；加指标必须改代码
2后端 snapshot资产/负债/权益/表外余额：按 _classify+_is_leaf 写死汇总 资产负债类指标不在指标体系内
3后端 snapshot贷款利率：写死 S01010101~05 前缀 + 余额加权 账户册编码一变就失效
4前端 ReverseDashboard.tsxMETA 常量（label/color/unit/desc）5 条 指标元数据在前端，加指标要改前端
5前端METRIC_KEYS = ['ROE','CET1','LCR','NSFR','DELTA_EVE'] 同上
6前端METRIC_TO_REG_CODE 映射（ROE→REG_ROE…） 前后端命名不一致，映射靠前端兜
7前端 KPI 区 JSX资产/负债/贷款利率 3 张卡 + ROE 1 张卡硬编码 无法参与动态选择
8前端 KPI 区 JSX其余 4 张卡按 METRIC_KEYS map 同上

1.3 现状：模型侧 4 个缺口

#缺口现状与影响
1没有"是否评分"标识 现在靠"配没配 score_rule"隐式决定：REG_CAR / REG_IBL / REG_LR 有定义但没规则 → 实际不参与评分， 但列表里看不出意图，换个人接手就不知道是"还没配"还是"故意不评"
2指标定义与引擎指标命名不一致 prcp_kpi_definition.kpi_code = REG_ROE； prcp_metric_coefficient.metric_code = ROE； DELTA_EVE ↔ REG_EVE —— 靠前端硬编码映射
3指标方案没被组合方案引用 prcp_kpi_scheme 有 2 条（kpi_count 都是 0，未维护）， 但 prcp_reverse_scheme 没有 kpi_scheme_id → "方案对应的所有指标"目前无来源
4scheme_id 同名不同义（隐患） prcp_kpi_definition.scheme_id 指指标方案； prcp_metric_coefficient.scheme_id 指账户册方案 —— 同名不同义，极易写错
缺口 4 建议在本期一并处理：这是"来源统一"的隐性前提 —— 后面要做指标动态取数， 一旦按 scheme_id 关联，混用会导致取到空数据且难以排查。

设计目标与原则

2.1 三个目标

目标说明验收
G1指标定义唯一来源 首页展示的每一个指标卡，都能在 prcp_kpi_definition 里找到对应一行； 前端不再有指标名/单位/口径的硬编码
G2计算与评分解耦 每个指标显式声明 is_scored；为 0 时照常计算并展示，但不进总分、不出评分标签
G3首页动态多选 齿轮面板列出方案全部可选指标，多选控制展示；默认选中前 8 个；用户选择可持久化

2.2 设计原则

  • 配置驱动，不改代码：新增/下线一个展示指标 = 改一条 kpi_definition 记录，不动前后端代码
  • 向后兼容：现有 5 个监管指标的展示与评分结果必须完全不变（回归硬约束）
  • 评分规则独立：is_scored=0 的指标不要求配 score_rule，也不出现在评分明细里
  • 口径可追溯：每个指标的口径描述（formula_desc）随卡片一起下发给前端（Tooltip 展示）

关键设计点：指标定义承载「是什么 / 从哪算 / 是否评分 / 怎么展示」四件事， 首页只做「按用户选择渲染」，不再关心口径。

3.3 scheme_id 语义隐患的处理

prcp_kpi_definition.scheme_id（指标方案）与 prcp_metric_coefficient.scheme_id（账户册方案）同名不同义。

方案改动量说明
A. 改名（推荐）中 prcp_metric_coefficient.scheme_id → coa_scheme_id， scheme_code → coa_scheme_code。语义自解释，从此不可能写错。 需同步改引擎写入与后端读取（约 4 处）
B. 只加注释小 表/字段 COMMENT 说明"此处为账户册方案"。零代码风险，但靠人记
C. 保持现状无 不推荐 —— 本期要做的正是"按指标定义取数"，混用会取到空数据且难排查
建议：本期做 A（改名 + 迁移脚本），同时在 prcp_kpi_definition 上把字段保留为 scheme_id 并在 COMMENT 标注 "指标方案 id"；两者靠字段名本身区分（scheme_id vs coa_scheme_id）， 比 A/B 混用更安全。

取数方式与计算链路

4.1 四种 value_source

value_source适用指标 取数逻辑数据表
ENGINE_METRICROE / CET1 / LCR / NSFR / EVE 按 metric_code 从系数表取该节点的值，再按指标口径聚合 （现为节点算术平均；ROE/NIM 等有特殊口径的走既有实现） prcp_metric_coefficient
BS_CATEGORY_SUM资产/负债/权益/表外余额 按 source_params.category 取末级节点余额求和（复用现有 roll-up 口径） prcp_data_reverse
NODE_WEIGHTED_RATE贷款加权平均利率 按 source_params.node_pattern 匹配节点（默认 L4 以下）， 以 current_balance 为权重的 weighted_rate 加权平均 prcp_data_reverse
KPI_VALUE基期对比兜底 直接取指标值表（当前 prcp_kpi_value），用于无反算结果时的回退展示 prcp_kpi_value
口径一致性硬约束： BS_CATEGORY_SUM 与 NODE_WEIGHTED_RATE 必须复用现有 snapshot 的同一套计算代码 （_classify + _is_leaf + 同样的节点过滤），只是把"写死"改成"由配置指定"。 不允许重写一套 —— 否则改造前后数值会对不上，回归无法通过。

4.3 评分侧解耦

环节改造点
评分明细接口只返回 is_scored=1 的指标（kpi_scores[]）
总分计算只对 is_scored=1 且有 segment 的指标加权累加
目标达成prcp_reverse_target 仍可给非评分指标设目标（如资产余额 ≥ 某值）， 达成度照常算，但不进总分
前端 ScoreTag只在 is_scored=1 且有评分记录时渲染
评分规则维护页勾选"参与评分"的指标才允许配 score_rule；未勾选的隐藏该配置入口
兼容保证：现有 5 个监管指标 is_scored 置 1， 评分规则、分段、总分口径一字不改 → 现有评分结果与反算结果保持一致（回归硬约束）。

风险与边界

#风险等级应对
1口径漂移：新写的取数逻辑与现有 snapshot 算法不一致高 不重写算法，抽取现有代码复用；P2 验收做逐指标对拍，误差必须为 0
