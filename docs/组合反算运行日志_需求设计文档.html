需求与目标

1.1 需求描述

编号需求项说明
R1日志实时刷新调用过程中日志能实时刷新，可按时间间隔定时请求刷新
R2日志反映运行状态日志不是孤立的文本流，要能表达「当前处于哪个阶段、进行到第几轮、整体进度多少」
R3多轮推算逐轮记录如果是多轮推算，日志中记录每一轮的状态和结果

1.2 设计目标

  • 把「运行记录」从纯文本追加流升级为结构化可观测过程
  • 接口形态与《资负反向测算接口文档》的 progress / history / trace 契约对齐，便于后续对接决策中心
  • 轮次记录独立成表，日志流只承载摘要，避免大 JSON 塞进日志表

1.3 非目标

  • 不引入新的优化算法（ACOR/DE/SLSQP 多引擎属决策中心侧能力）
  • 不做分布式追踪 / 链路埋点
  • 不改造结果存储结构（prcp_reverse_result 保持不变）

3.2 关键设计决策

决策方案理由
轮次记录载体独立新表 + 日志流只写摘要 轮次结果含指标 JSON，量大；混在日志表会让日志查询变重、也无法按轮次聚合
轮次语义一次反算任务内的一次求解尝试 = 一轮 与文档 trace[].iter 语义一致（粗筛迭代轮次）
单轮兼容单轮算法记为 round_no = 1 现有 QP/LP 是单次求解，不改算法但结构就位
多轮如何落地HEURISTIC 改为 5 轮迭代改进 HEURISTIC 本是演示算法，改它风险最低，且能让多轮记录被真实验证
轮次得分口径按目标约束算达成度 → 0~500 不依赖评分规则表（prcp_kpi_value 是基期预存值，不适用于轮次）
进度来源run.progress ∪ 最新日志 progress 取大 run 表 progress 仅在结束时写 100，运行时为 0，不取会导致进度条不动
轮询策略间隔由后端下发；页面隐藏暂停；done 自动停 对齐 poll_interval_ms 契约，同时避免后台页无意义请求

引擎侧轮次编排

6.1 编排流程

# 轮次编排器（伪代码） def _run_rounds(db, run_id, algo_fn, algo_code, bal_data, targets): max_round = ALGO_ROUNDS.get(algo_code, 1) # QP/LP=1，HEURISTIC=5 best_result, best_score = None, None for r in range(1, max_round + 1): _round_start(db, run_id, r, algo_code) # 轮次开始 → status=RUNNING _log(... "第 r/max_round 轮开始", stage=SOLVE, round_no=r) try: res = algo_fn(bal_data, targets, log_fn_r, round_no=r) except Exception as e: _round_end(... status=FAILED, message=str(e)) # 轮次失败也要落库 raise score, hit = _round_score(res) # 达成度 → 0~500 分 _round_end(... status=SUCCESS, score=score, optimal_value=ov, target_hit=hit) _log(... "第 r 轮完成：opt=..., 得分=...", round_result={score, optimal_value, target_hit}) if 更好: best_result, best_score = res, score # 取最优轮 return best_result

6.2 轮次得分口径（_round_score）

约束类型达成度说明
GE（≥）实际 / 目标越高越好
LE（≤）目标 / 实际越低越好
EQ（=）1 − |实际 − 目标| / |目标|
加权得分 = Σ(达成度 × 权重) / Σ权重 × 500 # 归一到 0~500 分制 target_hit = 所有 GE 目标实际 ≥ 目标 且 所有 LE 目标实际 ≤ 目标

6.3 阶段打点位置

代码位置stage说明
任务启动后SUBMIT记录方案与算法
读取目标后LOAD_TARGET记录目标条数
读取账户册后LOAD_BALANCE记录账户册数与月份数
进入求解SOLVE轮次内逐条打点
写结果前SAVE_RESULT
成功收尾DONE携带 optimal_value
异常收尾FAILED携带错误信息

6.4 多轮如何真正跑起来

HEURISTIC 改造为 5 轮迭代改进
  • 第 1 轮：初始解（历史均值 + 趋势外推）
  • 第 r 轮：在上一轮基础上加确定性扰动（种子 20260101 + round×977，保证可复现）， 扰动幅度按 0.02 × 0.7^(r−1) 递减，再做一次收缩改进（向跨月均值靠拢）
  • 每轮评估目标函数（波动度），由编排器择优
说明：QP / LP 仍是单轮求解（round_no = 1）。当后续接入决策中心的 ACOR / DE / SLSQP 多引擎时，只需在 ALGO_ROUNDS 中登记轮数， 由引擎在每轮迭代前后调用 _round_start / _round_end 即可， 日志与轮次表结构无需变更。

8.2 异常处理

场景行为
轮次内算法抛异常该轮记 FAILED（含错误摘要与耗时）→ 写一条 ERROR 日志 → 整轮任务标记 FAILED
日志表未迁移_log / _round_* 捕获异常并回滚，不阻塞主流程（反算结果仍能写出）
轮次表查询失败/progress 与 /rounds 返回空列表，不影响日志展示
轮次中途取消轮次状态记 CANCELLED；progress.cancelled = true
前端请求失败catch 后 console.error，不中断定时器，下轮继续

验证与遗留

9.1 验证结果

验证项结果实测
轮次记录通过 HEURISTIC 方案跑出 5 轮，轮次表逐轮记录 SUCCESS / 得分 500 / opt=0.0 / 耗时
日志结构化通过 27 条日志中 20 条带轮次标记；阶段齐全 SUBMIT / LOAD_TARGET / LOAD_BALANCE / SOLVE / SAVE_RESULT / DONE
progress 契约通过 done / success / cancelled / percent / stage / round_no / rounds[] / poll_interval_ms 齐备
进度实时性通过 运行中 percent = 80.00（不再恒为 0），结束时 100.00
当前轮次通过 运行中与结束后均为「第 5 轮」，不出现空值
前端轮次面板通过 抽屉内 5 张轮次卡（轮次/算法/结论/耗时/得分/目标值/达成），日志行带 [R1]~[R5] 与阶段标签

9.2 遗留问题

编号问题等级说明与建议
L1QP / LP 仍是单轮中 多轮结构已就位，ALGO_ROUNDS 登记轮数即可扩展；接入 ACOR/DE 时在每轮前后调用 _round_start/_round_end 即可，无需改表结构
L2轮次得分未用评分规则表低 当前按目标约束算达成度；prcp_kpi_value 是基期预存值，不适用于轮次级实时评分
L3取消时轮次状态未落 CANCELLED低 引擎在每轮迭代前检查取消标志；当前取消会中断任务但正在跑的轮次仍是 RUNNING，需补一次状态回写
L4日志表无清理策略低 长周期运行会累积；建议按 run 保留 N 天或按 created_at 定期归档
L5未与决策中心网关打通低 本方案是 PRCP 内部形态；如需对外暴露网关入口，按文档「统一 POST + action 区分」改造即可
