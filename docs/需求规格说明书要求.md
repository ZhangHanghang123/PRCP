需求文档编制规范

- 原模板中已有的文字必须逐字保留，包括标题、字段名称、表头、编写指引、说明、备注、优先级次序及定义、标点等；不得自行删减、改写、概括、纠错或用本项目规则替换。仅在模板指定的填写区域补充需求内容；除用户明确指定的具体修改外，不得改动模板原文。字段默认值和业务内容要求只作用于填写内容，不构成修改模板原文的授权；存在冲突时在说明书外沟通，不擅自处理。
- 需求规格说明书只纳入已确认的需求与业务事实，未确认、待确认事项不得写入正文、表格、图示、附录或备注，也不得设置“待确认事项”清单或以“待确认”“未确认”“TBD”等占位。此类事项在说明书外单独沟通或保留于内部上下文 spec，不得仅删除不确定性标签后作为确定需求写入；涉及必填内容或影响需求完整性的关键事项，应先取得确认再完成对应内容，不得虚构或擅自填写“无”“不涉及”。交付前须检查并排除未确认、待确认事项。
- 需求文档中本项目的系统名称统一写为“组合管理测算平台PRCP”，不得自行创造、缩写或替换该名称。
- 需求规格模板中的“系统标识”默认填写“PRCP”（全大写），适用于模板内所有同名字段，包括整体系统功能分布表及特性条目中的相关字段；“系统名称”仍填写“组合管理测算平台PRCP”，不得混用。只有用户或已确认的正式需求明确涉及其他系统时，才填写其已确认的系统标识；不因本规则新增或改写模板表头。
- 除非用户或已确认的正式需求特别明确涉及其他系统，关联系统均统一写为“组合管理测算平台PRCP”。本要求适用于正文、整体系统功能分布表、整体系统功能分布图及特性级系统链路图；不得根据模块名称、功能分工、数据来源或技术组件自行推断并新增独立系统。未明确其他系统时，各功能均归属“组合管理测算平台PRCP”，可在该系统内区分模块或功能；明确涉及其他系统时，才使用其已确认的正式名称并列明相应改造及配合测试情况。
- 需求文档中的表格边框统一使用实线。
- 需求规格文档中的表格必须严格按照用户指定或已确认的原始模板填写。编写前先读取模板对应表格，逐字保留表头名称、标点、列数、列序、多级表头及合并单元格结构，只在对应内容单元格填写需求内容、按需增加数据行；未经用户明确要求，不得自行新增、删减、改名、合并、拆分或重排表头，不得用概括性字段清单或历史生成文档代替原模板。
- 交付前须将各表表头与原模板逐项核对，重点检查“2.1.2 整体系统功能分布表”；业务内容要求应映射到模板原有栏目，补充说明放在适当的内容单元格或表外文字中，不因需要补充说明而增加或改写表头。模板未提供或对应表头无法确认时，不得凭经验猜测表头。
- 交付前还须将模板已有文字与原模板逐项核对，不限于表头，重点检查备注、编写指引及优先级说明，确保无未经用户明确授权的修改或遗漏；发现误改时按原模板恢复，不凭记忆补写。同时核对对应段落和文字的实际格式属性，并通过渲染检查确认段落间距、字体、字号及其他文字格式与模板一致，不能只检查文字内容。
- 除下述首行缩进要求外，需求规格说明书的段落间距与文字格式、大小必须严格沿用原模板对应位置的设置，包括段前距、段后距、行距及其类型、左右缩进、对齐方式，以及中西文字体、字号、加粗、斜体、下划线、颜色和字符间距。标题、正文、表格文字、备注、编写指引等分别保留其原有格式，不得全篇统一重设；原“正文统一使用宋体五号”的要求不再作为覆盖模板格式的依据。
- 正文普通自然段采用首行缩进两个中文字符，通过段落格式设置，不用空格或制表符模拟；带有编号的内容及表格内所有段落不设置正文式首行缩进。编号列表的编号对齐、层级排版及表格单元格内边距仍沿用模板，不因取消首行缩进而改动。本要求作为模板格式继承规则的明确例外，优先用于对应段落的首行缩进；不改动模板已有文字，其他段落及文字格式保持模板原样，交付前分别核对正文、编号内容和表格内容。
- 在模板指定区域填写或新增内容时，继承对应区域或同类段落、单元格的样式及直接格式，不因替换文字、增加段落或数据行而丢失格式；不得为压缩页数或调整视觉效果擅自改变字号、段落间距、行距，或用额外空行代替模板间距。模板格式无法确认时，应先读取原模板或在说明书外沟通，不凭经验设置。
- 需求规格说明书中需填写或新增的普通序号统一使用阿拉伯数字“1、2、3……”顺序编号，同一表格或列表内连续递增；表格“序号”列填写纯数字，不使用中文数字、罗马数字、带圈数字或特性条目编号代替普通序号。本规则不改动模板已有的编号、文字和格式；章节编号、特性条目编号及原型编号等专用标识仍按模板及已确认的对应规则填写。
- 原型编号必须严格采用“特性条目编号-Pxx”格式，并在同一特性条目内从 P01 顺序编号，例如 `F01-P01`、`F01-P02`。
- 特性条目标题不写“标准特性条目-功能类”等模板分类文字，直接使用“Fxx+特性条目名称”格式，例如“F01贷款息差测算页面功能”。
- 需求规格模板中的“系统功能条目”必须严格按照对应的已确认特性条目名称逐字填写，适用于整体系统功能分布表及模板内其他同名字段；不得缩写、概括、改名，或用模块名称、功能描述、改造说明代替特性条目名称。涉及多个特性条目时，按模板填写方式逐项列明各自完整名称，不合并为自拟名称；编号按模板对应字段及既有编号规则填写，不代替名称。交付前须与特性条目清单及对应章节逐项核对名称一致性，不因本规则修改模板已有表头、文字或格式。
- 需求规格模板中的“优先级”字段值默认填写“P1”，适用于模板内所有同名字段，包括特性条目中的优先级；只有用户或已确认的正式需求明确指定其他优先级时，才按其要求填写，不自行推断或调整。本规则仅用于填写字段值，不因本规则新增或改写模板表头；模板中以“备注：优先级次序为”开头的整句及其后续说明必须按原模板完整保留，不得改成“优先级默认P1”或修改其中的次序、定义、标点。
- 需求规格模板中的“是否仅配合测试”默认填写“否”，表示需要开发或改造；只有用户或已确认的正式需求明确无需开发、仅配合测试时才填写“是”。保留模板原字段名称，不得改写或理解为“是否配合测试”；填写“否”不代表无需测试。该规则适用于模板内所有同名字段，包括整体系统功能分布表及特性条目中的相关字段。
- 页面功能类特性条目下的“其他”栏须填写异常处理要求，内容为：“异常处理：单一功能异常时，应进行异常捕捉并向用户展示友好提示，不得导致整个应用崩溃、白屏或者中断运行。”仅在该栏对应填写区域补充内容，不将模板原有“其他”标题改为“异常处理”，不改动模板已有文字、段落间距或文字格式；交付前逐项检查页面功能类特性条目是否已填写该要求。
- 后续编制或修订需求规格文档时，“1.1 背景及必要性、现状和业务目标”必须围绕本次需求，从业务视角撰写，不描述技术方案、系统架构、数据库、接口或代码实现。
- 该节正文固定为以下三个独立自然段，依次以“背景及必要性：”“现状：”“业务目标：”开头；标签与内容写在同一段，不合并、不改为列表或表格。下述说明是撰写指引，生成文档时须替换为与本次需求相关的具体业务内容，现状依据已确认事实，目标不得虚构承诺或量化指标。

背景及必要性：说明本次需求所处的业务背景、管理诉求及提出需求的原因，阐明解决相关业务问题的必要性。

现状：说明当前业务办理、测算或分析的实际方式、已具备的业务能力及存在的不足，明确这些问题对业务工作的影响。

业务目标：说明本次需求预期解决的业务问题、希望达到的管理效果和业务价值，围绕效率、准确性、分析能力或决策支持等与需求相关的方面展开。

### 2.1.1 整体业务流程

- 本节描述需求维度的整体业务流程。编写前先从业务操作角度判断各特性条目之间是否存在先后顺序、相互调用、包含等关联关系，以及这些条目是否共同构成或完成一项相对完整的业务；不得仅因存在多个特性条目就强行编制统一流程。
- 多个特性条目存在上述业务关联时，必须绘制整体业务流程图，并可配合文字说明。图中从实际参与的客户或内部用户等角色视角，按各角色完成的事项描绘业务逻辑，明确各阶段或步骤由谁执行、主要操作内容及业务衔接，清晰展现需求全貌。角色须依据实际需求，不虚构客户、柜员或审批角色。
- 整体业务流程图不夹杂系统交互链路，不以系统、服务或接口之间的调用代替用户角色的业务操作。特性条目的系统交互链路统一在对应特性条目章节中绘制。
- 需求为一个或多个简单优化点，且优化点相对独立、无较强逻辑关系、没有整体业务逻辑，或难以形成有业务意义的统一流程时，无需绘制整体业务流程图，也无需描述整体业务流程；应在本节简要说明不适用的原因，具体业务流程在各特性条目章节分别描述。
- 无关联时可表述为：“本次需求各特性条目相对独立，不存在构成统一业务流程的先后顺序、相互调用或包含关系，无需编制统一的业务流程图；各特性条目的具体业务流程在对应章节分别描述。”须按实际情况调整，不能对有关联的需求套用该说明。

### 2.1.2 整体系统功能分布

- 整体系统功能分布表为所有需求的必填内容，包括单个特性条目和相互独立的简单优化点，不因无需绘制整体业务流程图或整体系统功能分布图而省略。以表格列明本次需求涉及的全部系统，覆盖实际涉及的功能系统、数据系统和智能化系统，逐项说明功能分工、改造情况及配合测试情况，帮助读者了解需求涉及的系统全貌；无需改造但需配合测试的系统也必须纳入。
- 本节直接复用原模板的整体系统功能分布表，表头名称、数量、顺序及合并结构以原模板为准，不另行规定或自拟表头。功能分工、改造情况及配合测试情况按模板原有栏目的含义填写；模板中的“是否仅配合测试”默认填“否”，系统名称遵循上述关联系统默认命名规则。具体改造范围和测试范围依据已确认的实际需求填写，未确认、待确认事项不写入说明书，按上述确认规则在说明书外处理，不虚构系统或配合事项。
- 当特性条目之间存在关联关系、需求具有整体业务流程时，必须绘制需求维度的整体系统功能分布图。图中体现需求涉及的全部关联系统、各系统承担的功能及系统间交互关系，并在交互连线上标明批量或实时方式；同一系统间兼有两种方式时分别标注。可按需将关联系统归为渠道入口类、功能类、数据类、智能化类等，分类以实际需求为准。
- 若需求为一个或多个简单优化点，优化点之间无较强关联关系，则无需绘制整体系统功能分布图，应简要说明不适用原因，并在对应特性条目章节绘制特性级系统链路图；整体系统功能分布表仍须填写。
- 本节是否绘制整体系统功能分布图，应与“2.1.1 整体业务流程”对特性条目关联关系的判断保持一致。整体系统功能分布图用于表达系统功能分工与交互，不混入2.1.1的用户角色业务流程图。
